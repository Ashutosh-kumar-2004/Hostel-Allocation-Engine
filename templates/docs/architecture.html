System Architecture & Operational Flowcharts

Visual diagrams representing the 3-role governance, bed-level allocation pipeline, Warden single-hostel boundaries, and room change workflow.

Figure 1 — Student Application & Allocation Flow

Student Intake → Consent → Eligibility Check → Draft Output → Explanation Result

Role: Student
Key Step 1: Intake & Consented Data Applicant fills student details, uploads documents, selects ranked hostel & room types, and provides consent for lifestyle survey.
Key Step 2: Policy Rule Validation System verifies distance, CGPA, and disciplinary rules. Failed rules immediately flag applicant as ineligible with clear reasons.
Key Step 3: Transparent Explanation Once published, students can view their allotment letter and complete breakdown of why that specific bed was assigned.

Figure 2 — Warden Allocation & Publication Flow

Draft Generation → Mandatory Review → Manual Overrides → Formal Approval Gate → Final Publication

Role: Warden
Structural Governance Guarantee The allocation engine only ever writes an AllocationDraft. Direct writing to published state is barred by database foreign-key constraints.
Mandatory Override Justification Wardens can reassign any bed on the interactive bed map, but must provide a mandatory textual explanation stored in immutable audit logs.
Recorded Human Approval Gate Publication triggers background WeasyPrint PDF generation only when a signed WardenApproval record is in place.

Figure 3 — System Administrator Warden Assignment Flow

1 Warden to 1 Hostel Assignment & Reassignment with Object-Level Boundary Enforcement

Role: System Admin
1-to-1 Hostel Assignment Admin assigns exactly one Warden to each hostel through WardenHostelAssignment.
Object-Level Queryset Filtering Warden view permissions are checked server-side via filtered querysets (filter(hostel=warden.hostel)), preventing URL guessing attacks.
Reassignment Auditing Admin can reassign wardens when academic terms rotate. Every change logs prior and new assignments into the audit trail.

Figure 4 — Hostel Inventory Hierarchy

Hostel → Block → Floor → Room (Cooling: AC / Cooler / None) → Bed (Final Allocation Target)

Inventory Data Architecture
Granular Hierarchy Hostel has multiple Blocks; each Block has Floors; each Floor contains Rooms; and each Room contains Beds.
Variable Room Capacities Room capacity is dynamic and derived from the count of bed records (e.g. Room A-102 has 4 beds; Room A-103 has 6 beds) rather than a rigid table column.
Cooling Types Rooms specify cooling independently: AC, Cooler, or None.

Figure 5 — Room Change Request Flow

Student Request Submission → Warden Review → Bed Reallocation → Audit History Log

Post-Allocation Operational Workflow
Student Self-Service Request Students submit a request specifying preferred cooling, room type, and a mandatory detailed reason.
Warden Decision Hub The assigned Warden inspects live vacancies and either approves the request with a new bed allotment or records a rejection reason.
Atomic Bed Release & Allocation On approval, the prior bed is set to Available and the target bed is occupied in an atomic transaction with an AuditEntry.
